# マイノート管理アプリ開発 Constitution

## 基本原則

### I. 最新の安定バージョン利用

すべてのフレームワークおよびライブラリは、最新の安定バージョン（Stable Release）を使用すること。

**根拠**: セキュリティパッチ、パフォーマンス改善、最新機能の恩恵を受けるため。また、技術的負債の蓄積を防ぎ、
長期的な保守性を確保する。ベータ版やアルファ版は本番環境では使用しない。

**技術スタック対象**:
- Python: 安定版（執筆時点では 3.11 以上推奨）
- FastAPI: 最新安定版
- React: 最新安定版
- Vite: 最新安定版
- TypeScript: 最新安定版
- Terraform: 最新安定版

### II. 型安全性の厳守

すべてのコードは型安全でなければならない。TypeScript は strict mode で運用し、Python はすべての
関数・メソッドに type hints を付与すること。

**根拠**: 型安全性は実行時エラーを開発時に検出し、IDEによる補完・リファクタリング支援を可能にする。
これによりコード品質が向上し、バグの早期発見とメンテナンス性の向上を実現する。

**必須要件**:
- TypeScript: `tsconfig.json` で `"strict": true` を設定
- Python: すべての public API に type hints を記述し、mypy などの型チェッカーで検証
- 型定義ファイル（`.d.ts`、`.pyi`）の適切な管理

### III. テスト駆動開発（TDD）の採用

すべての開発はテスト駆動開発（TDD）に従い、テストから書き始めること。

**根拠**: TDD は設計品質を向上させ、リグレッションを防止し、リファクタリングを安全に行える基盤を提供する。
Red-Green-Refactor サイクルを遵守することで、必要最小限の実装と高いテストカバレッジを両立する。

**TDD サイクル**:
1. **Red**: 失敗するテストを書く
2. **Green**: テストを通すための最小限の実装を行う
3. **Refactor**: コードを改善する（テストは通ったまま）

### IV. API ユニットテスト必須

すべての API エンドポイントには対応するユニットテストを記述すること。

**根拠**: API は外部インターフェースであり、契約違反は重大な障害につながる。ユニットテストにより、
各エンドポイントの正常系・異常系の動作を保証し、リグレッションを防ぐ。

**必須テスト観点**:
- 正常系: 期待される入力に対する正しい応答
- 異常系: 不正な入力に対する適切なエラーハンドリング
- 境界値: エッジケースの検証
- 認証・認可: セキュリティ要件の検証

### V. コミット前リンター実行の必須化

すべてのコミット前に、リンターおよびフォーマッターを実行すること。

**根拠**: コードスタイルの統一により、レビュー時の無駄な議論を削減し、可読性を向上させる。
自動化により人的ミスを防ぎ、CI/CD パイプラインでの失敗を未然に防ぐ。

**ツール要件**:
- Python: `black`（フォーマット）、`ruff` または `pylint`（リント）
- TypeScript/JavaScript: `eslint`（リント）、`prettier`（フォーマット）
- Terraform: `terraform fmt`、`tflint`
- Pre-commit hooks の活用を推奨（`.pre-commit-config.yaml`）

### VI. シークレット管理の徹底

シークレット（API キー、パスワード、証明書など）はコードに含めず、環境変数または専用のシークレット
管理サービスを使用すること。

**根拠**: シークレットがコードに含まれると、リポジトリ履歴に永続化され、漏洩リスクが高まる。
環境変数や専用サービスの利用により、セキュリティインシデントを防止する。

**必須対策**:
- `.env` ファイルは `.gitignore` に追加
- Azure Key Vault などのシークレット管理サービスの利用
- CI/CD 環境では GitHub Secrets や Azure Pipelines Variables を使用
- コードレビュー時のシークレット混入チェック
- `git-secrets` や `truffleHog` などのスキャンツール導入を推奨

## 品質基準

以下の品質基準を満たすこと。基準を満たさないコードは原則としてマージしない。

**コードカバレッジ**:
- ユニットテスト: 80% 以上（目標: 90%）
- API エンドポイント: 100%（全エンドポイントにテスト必須）

**静的解析**:
- リンターのエラー: 0 件
- 型チェックのエラー: 0 件
- セキュリティスキャンの Critical/High 脆弱性: 0 件

**ドキュメント**:
- すべての public API に docstring またはコメントを記述
- README.md にセットアップ手順とクイックスタートを記載
- API エンドポイントは OpenAPI（Swagger）で自動ドキュメント化

## 開発ワークフロー

**ブランチ戦略**:
- `main`: 本番環境デプロイ可能な状態を常に維持
- `develop`: 開発用統合ブランチ
- `feature/*`: 機能開発用ブランチ
- `hotfix/*`: 緊急修正用ブランチ

**コードレビュー**:
- すべての変更は Pull Request を経由し、最低 1 名のレビューを必須とする
- レビュー観点: 機能要件、テストカバレッジ、コードスタイル、セキュリティ、パフォーマンス
- 自動化テストが通過していない PR はマージしない

**コミットメッセージ**:
- Conventional Commits 形式を推奨（例: `feat:`, `fix:`, `docs:`, `test:`）
- 日本語で記述可能だが、英語を推奨

**リリースプロセス**:
- セマンティックバージョニング（SemVer）に従う
- リリースノートを作成し、主要な変更を記載

## ガバナンス

本憲章は、すべての開発プラクティス、技術選定、コードレビューに優先する。
憲章に反する実装は、正当な理由がない限り認められない。

**憲章の修正手順**:
1. 修正提案をチームに共有
2. チームでの議論と合意形成
3. 本ドキュメントの更新
4. バージョン番号の更新（セマンティックバージョニングに従う）
5. 依存する成果物（テンプレート、ドキュメント）の同期更新

**コンプライアンス検証**:
- すべての Pull Request レビュー時に憲章遵守を確認
- CI/CD パイプラインで自動チェック可能な項目（リンター、型チェック、テストカバレッジ）は自動化
- 四半期ごとに憲章の有効性をレビューし、必要に応じて改訂

**例外処理**:
- 憲章に従うことが技術的に困難または不合理な場合は、チームでの議論と合意により例外を認める
- 例外は Pull Request の説明に明記し、理由を文書化すること
