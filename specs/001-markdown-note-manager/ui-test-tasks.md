# タスク: frontend UI テスト実装

**入力**: `/specs/001-markdown-note-manager/ui-test-plan.md` のテスト実装計画書
**前提条件**: `ui-test-plan.md` (必須), `spec.md` (機能要件), `plan.md` (技術スタック)

**Constitution 準拠**: すべてのタスクは `.specify/memory/constitution.md` の基本原則に従うこと

- TDD（テスト駆動開発）を採用: テストを先に書き、実装前に失敗を確認（Red-Green-Refactor）
- すべての API にユニットテストを記述
- 型安全性の確保（TypeScript strict mode）
- コミット前にリンター・フォーマッターを実行
- テストカバレッジ 80% 以上を維持

**構成**: タスクは優先度（P0, P1, P2）ごとにグループ化されており、段階的な実装が可能です。

## フォーマット: `[ID] [P?] [TestType] 説明`

- **[P]**: 並列実行可能（異なるファイル、依存関係なし）
- **[TestType]**: テストタイプ（E2E, Unit, A11y, Perf）
- 説明には正確なファイルパスを含める

## パス規約

このプロジェクトはフロントエンドテストに焦点を当てており、以下の構造を使用します:

- **E2E テスト**: `frontend/tests/e2e/`
- **ユニットテスト**: `frontend/tests/unit/`
- **アクセシビリティテスト**: `frontend/tests/a11y/`
- **パフォーマンステスト**: `frontend/tests/performance/`

## リスクと軽減策

### リスク 1: FR-020（MongoDB 接続エラー）のテスト困難性

**リスク**: バックエンドの停止/起動を制御する必要があり、テスト環境のセットアップが複雑

**軽減策**:
- Playwright の `route` API を使用してネットワークリクエストをインターセプト
- レスポンスを意図的にエラーにすることで、接続エラーをシミュレート
- 実際のバックエンド停止テストは手動テストで補完

### リスク 2: パフォーマンステストの不安定性

**リスク**: CI 環境の負荷によって、時間計測が不安定になる可能性

**軽減策**:
- 時間制約を厳密にしすぎず、余裕を持たせる（例: 500ms ではなく 600ms）
- 複数回実行して平均を取る
- CI 環境専用の設定ファイルを用意

### リスク 3: WYSIWYG ツールバー操作の E2E テストの複雑性

**リスク**: TipTap エディタの DOM 構造が複雑で、テストが脆弱になる可能性

**軽減策**:
- `data-testid` 属性を適切に配置
- ツールバーボタンには明確な `aria-label` を付与
- E2E よりもユニットテストで詳細にテスト

## 注意事項

- [P] タスク = 異なるファイル、依存関係なし
- [TestType] ラベルはテストタイプを明示（E2E, Unit, A11y, Perf）
- 各タスクは独立して完了可能かつテスト可能であるべき
- 各タスクまたは論理的なグループの後にコミット
- 任意のチェックポイントで停止してテストを検証可能
- 避けるべきこと: 曖昧なタスク、同一ファイルの競合、独立性を壊す依存関係
