# UI テスト実装計画書: Markdownノート管理アプリ

**作成日**: 2026-02-16
**対象プロジェクト**: `001-markdown-note-manager`
**仕様書**: [spec.md](./spec.md)

## 概要

本計画書は、frontend の UI テストの現状を分析し、不足しているテストシナリオを特定して、包括的な UI テスト実装計画を提供します。

### 目的

- 既存の UI テストカバレッジを評価する
- 機能要件とユーザーストーリーに対するテストギャップを特定する
- 不足しているテストシナリオを優先度付けして実装計画を作成する
- テストの品質基準（QC-001: 80% 以上）を達成する

### 対象範囲

以下のテストタイプを対象とします：

1. **E2E テスト** (Playwright): ユーザーフロー全体の統合テスト
2. **ユニットテスト** (Vitest + React Testing Library): コンポーネントの単体テスト
3. **アクセシビリティテスト** (axe-core): WCAG 2.1 AA 準拠の検証
4. **パフォーマンステスト** (Playwright): 成功基準（SC-003, SC-005, SC-008）の検証

## テストギャップの特定

### 高優先度（P0）: 機能要件の未実装

1. **FR-018**: 未保存変更の確認ダイアログ
   - **不足**: E2E テスト、ユニットテスト
   - **理由**: データ損失を防ぐ重要な UX 機能

2. **FR-019**: 重複タイトルの自動番号付加
   - **不足**: E2E テスト、ユニットテスト
   - **理由**: データの整合性とユーザビリティに関わる機能

3. **FR-020**: MongoDB 接続エラー表示
   - **不足**: E2E テスト（接続失敗シナリオ）
   - **理由**: エラーハンドリングの重要な機能

### 中優先度（P1）: エッジケースと成功基準

4. **SC-003**: プレビュー更新時間の計測
   - **不足**: パフォーマンステスト（500ms 以内の検証）
   - **理由**: 成功基準の明示的な検証が必要

5. **SC-004**: 大規模データでの起動時間
   - **不足**: パフォーマンステスト（100 個のノートで 3 秒以内）
   - **理由**: スケーラビリティの検証

6. **US3-3**: キャンセルボタンの動作
   - **不足**: キャンセルボタンクリック時の変更破棄テスト
   - **理由**: 現在は「一覧に戻る」ボタンのみテスト済み

7. **US5-2**: WYSIWYG ツールバーボタンの実際の動作
   - **不足**: フォーマット適用後の DOM 検証
   - **理由**: 現在はボタンの存在確認のみ

### 低優先度（P2）: カバレッジ向上

8. **アクセシビリティ**: 削除確認ダイアログ
   - **不足**: axe-core テスト
   - **理由**: WCAG 2.1 AA 準拠の完全性

9. **アクセシビリティ**: エラー状態
   - **不足**: axe-core テスト（空タイトルエラー時）
   - **理由**: エラー状態でのアクセシビリティ検証

10. **FR-008**: 更新日時の UI 表示検証
    - **不足**: 編集保存後の更新日時表示テスト
    - **理由**: データの正確性を UI で確認

11. **FR-014**: Markdown 変換の完全性
    - **不足**: WYSIWYG → Markdown の包括的な変換テスト
    - **理由**: すべてのフォーマット（見出し、リスト、リンクなど）の検証

## リスクと軽減策

### リスク 1: FR-020（MongoDB 接続エラー）のテスト困難性

**リスク**: バックエンドの停止/起動を制御する必要があり、テスト環境のセットアップが複雑

**軽減策**:
- Playwright の `route` API を使用してネットワークリクエストをインターセプト
- レスポンスを意図的にエラーにすることで、接続エラーをシミュレート
- 実際のバックエンド停止テストは手動テストで補完

### リスク 2: パフォーマンステストの不安定性

**リスク**: CI 環境の負荷によって、時間計測が不安定になる可能性

**軽減策**:
- 時間制約を厳密にしすぎず、余裕を持たせる（例: 500ms ではなく 600ms）
- 複数回実行して平均を取る
- CI 環境専用の設定ファイルを用意

### リスク 3: WYSIWYG ツールバー操作の E2E テストの複雑性

**リスク**: TipTap エディタの DOM 構造が複雑で、テストが脆弱になる可能性

**軽減策**:
- `data-testid` 属性を適切に配置
- ツールバーボタンには明確な `aria-label` を付与
- E2E よりもユニットテストで詳細にテスト

## 品質保証

### テストコードレビュー

すべてのテストコードは以下の基準でレビューします：

1. **可読性**: テスト名が明確で、何をテストしているか一目で分かる
2. **保守性**: 不要な重複がなく、変更に強い構造
3. **信頼性**: フレーク（不安定）なテストがない
4. **完全性**: エッジケースや例外パスもカバーしている

### CI/CD 統合

- すべてのテストは PR 作成時に自動実行される
- テスト失敗時は PR のマージをブロックする
- パフォーマンステストの結果をトレンドとして記録する

## まとめ

本計画書に従って UI テストを実装することで、以下の目標を達成します：

1. **機能要件の 100% カバレッジ**: FR-001 ~ FR-020 のすべてをテストで検証
